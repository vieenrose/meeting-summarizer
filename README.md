# Meeting Summarizer

在手機上即時產生長會議的可靠摘要：會議進行中由裝置端 ASR 轉寫，小模型逐段讀取，會後輸出分段摘要。目標是 1.5–3 小時、以台灣華語為主並夾雜英文的會議。摘要裡每一句都標註它所依據的逐字稿時間。

**狀態（2026-11-25）：研究階段。** v5 的最終候選已通過凍結測試（見「最新結果」），但那是 llama.cpp 的 Q4_K_M 檔。真正要發佈的是手機 app 引擎用的 `.litertlm`：在三個開發集上，它的矛盾率比 mobile-v2 低 3.3 個百分點、每千字矛盾句數少 41 %，但覆蓋率（0.54）仍低於目標 0.60，目前以蒸餾提高覆蓋率（見「下一步：v6 計畫」）。v5 尚未發佈；目前發佈的版本是 mobile-v2（見 [docs/mobile-v2.md](docs/mobile-v2.md)）。

## 下一步：v6 計畫

**目標：** 以 `.litertlm` 發佈、在手機 CPU 上執行的 Bolt 4GB（v5 架構、每段 32k），在下列七項同時勝過 mobile-v2，全部在 `.litertlm` 檔上量測，不再以 GGUF 代替。量化上限是平均每個權重 5 bits（不含 embedding）。

目前的模型是 `v4r2`：以問卷答對率為獎勵、經強化學習（GRPO）訓練的 Bolt 4GB。下表「目前」一欄是它的 `.litertlm`（DRY 取樣、以 `merge6` 合併主題），數字依序是財經節目（msdev，10 段）／立法院質詢（q12，24 段）／多人會議（ali20，20 段）。差異是三個開發集等權平均，括號內是以會議為單位重抽樣的 95 % 區間。

|---|---|---|---|---|
| 1 | 矛盾率 | 低於 mobile-v2 | 9.9 / 14.3 / 10.8 % 對 16.5 / 17.5 / 10.7 %：低 3.3 個百分點（−5.9 到 −0.6）；每千字矛盾句數少 41 %（−52 % 到 −28 %） | 勝出 |

| 7 | 架構 | v5（單次讀取、每段 32k、每段 3–6 個主題） | 54 / 54 段 | 符合 |

**標準的調整（11/25）：** 可讀性上限由 1,500 字放寬為 2,000 字，`[時間]` 引用不計入字數；覆蓋率目標由 0.65 調為約 0.60。手機上只做單次讀取，再以程式合併主題（`merge6`，整段最多 6 個主題，不改動句子），不加額外的生成步驟。

**轉換成 `.litertlm` 時發現並修正的問題：**
- 匯出的模型少了最後一層的 logit softcap（30·tanh(x/30)），輸出因此短了 31 %；改由引擎補上。
- 匯出時的 RoPE 複合運算會把位置固定住，長上下文逐漸偏移；改為不用該複合運算匯出，並以 teacher-forced KL 驗證。
- 用不帶懲罰的取樣時，`.litertlm` 有 2 / 10 段失控（重複標題或時間標記，寫到上限），同一模型的 GGUF 沒有。改用 DRY 與重複懲罰後失控消失（手機引擎也會採用這組取樣設定）；在 GGUF 的三個開發集、兩個 seed 上，這個設定不影響覆蓋率與每千字矛盾句數。

**接下來：**
1. **覆蓋率：** 在 GGUF 上，先寫初稿、再精簡、再補寫的三步驟流程，三個開發集的覆蓋率達 0.62–0.66，矛盾率不高於 mobile-v2，每千字矛盾句數少 29 %。但每多一步就多一次生成，手機上的時間會明顯增加。因此用 `v4r2` 對訓練用逐字稿產生這個流程的輸出，經評審刪去矛盾與無依據的句子後，以 LoRA 做 SFT，讓模型單次讀取就寫出同樣的結果。
   - **第一版 `sft3b`**（143 段目標、3 個 epoch，只用 ≥ 1,200 字的目標），在 GGUF 上是目前最好的單次讀取：覆蓋率 0.556 / 0.511 / 0.619（平均 0.562）；矛盾率比 mobile-v2 低 1.6 個百分點（−3.7 到 +0.6），每千字矛盾句數少 33 %。尚未達標之處：q12 有 3 段超過 2,000 字（可讀性 94.4 %，門檻 95 %），ali20 的無依據句子高 3.4 個百分點。它的 `.litertlm` 正在 CPU 上量測。
   - **發現的問題：** 評審是逐子句（以「；」與時間標記切分）判斷，建構訓練目標的程式卻以整句查詢判斷結果，含多個子句的句子從未被過濾，`sft3b` 的目標因此保留了約 8 % 被評審標記的內容。已修正。
   - **第二版 `sft4`（準備中）：** 以修正後的過濾、三個 seed 的流程輸出、偏好較長的目標重新建構訓練資料，並比較兩種提示：原提示，以及描述目標格式（以「；」串連一至三個事實、每個事實附時間）的提示。
2. 重新匯出 `.litertlm`，在三個開發集上量測七項。
3. 在 Samsung Galaxy A53 上量測 `.litertlm` 的記憶體與速度。
4. 在新的凍結測試集上只讀取一次（v5 的測試集已讀取過）。

## 架構（v5）

```mermaid
flowchart LR
    A[會議音訊] --> B[裝置端 ASR<br/>逐字稿]
    B --> C[在換講者處切段<br/>每段 ≤ 32k tokens]
    C --> D[Bolt 4GB 逐段讀取<br/>會議中預填 KV]
    D --> E[每段寫出主題小節<br/>以文法約束格式]
    E --> F[程式合併小節<br/>整場合計 3–6 個主題]
    F --> G[依小節標題與首句<br/>產生會議標題]
```

- **模型：** Nemotron-3.5-Bolt-E4B（4 GB），Q4 量化，只在手機 CPU 上執行。
- **分段：** Bolt 實測的有效上下文是 32k。整場一次讀到 64k 時，後段的覆蓋率會從 0.64 掉到 0.51，所以每次最多只讀 32k。
- **長度：** 整場會議 500 字加上每小時 250 字，上限 1,200 字，合計 3 到 6 個主題。可讀性比長度優先。
- **格式：** 由文法強制主題標題與 `[時間]` 引用。不輸出「決定」與「待辦」清單。
- **會議標題：** 寫完所有段落後產生。模型只看各小節的標題與首句，不看逐字稿，在手機上只需幾秒。
- **即時性：** 在 Samsung Galaxy A53 上用 app 引擎（融合注意力）實測如下。處理時間不超過會議長度。

  | 上下文 | 預填 | 解碼 | 記憶體 |
  |---|---|---|---|
  | 4k | 36.3 tok/s | 3.67 tok/s | 2.6 GB |
  | 32k | 12.4 tok/s | 1.33 tok/s | 2.83 GB |

## 評估方式

開發時，每一輪都在三個開發集上評估，各跑 4 個 seed：財經節目（msdev）、立法院質詢（q12）、多人會議（ali20）。

- **矛盾率：** 由 Qwen3.8-27B 判斷每一句與引用時間附近的逐字稿是否相符，分為「支持」、「矛盾」、「無依據」三類。
- **覆蓋率：** 讀者只拿到摘要，回答一份涵蓋整場會議的選擇題問卷，以答對比例計分（d3-turbo，與大型評審的 kappa 為 0.91）。
- **凍結測試：** 另外保留 120 場會議作為最終測試，開發期間不讀取。判定標準事先寫定，結果只讀取一次。
- **原則：** 不修正 ASR 輸出，也不排除長會議。

## 最新結果

**凍結測試（2026-11-17）：單次讀取的 Bolt 勝過 mobile-v2。** mobile-v2 是在 Gemma-4 E4B 上執行的閱讀代理，也是目前發佈的版本。

- **受測模型：** `g0mc`＝Bolt 4GB 併入句子層級 DPO 的 LoRA（`psent3n`）後重新量化為 Q4_K_M，精簡格式、不含清單，每場會議 4 個 seed。mobile-v2 每場一份段落摘要。
- **資料：** 120 場開發期間從未讀取的會議。下表每格依序是財經節目（24 場）／立法院質詢（25 場）／AISHELL-4（46 場）／AliMeeting（25 場）。
- **差異：** Bolt 減 mobile-v2，四個資料集等權；括號內是以會議為單位重抽樣得到的 95 % 區間。

| | mobile-v2 | Bolt（v5） | 差異 |
|---|---|---|---|
| 每千字矛盾句數（主要指標） | 7.48 / 9.73 / 5.78 / 7.52 | 4.67 / 5.66 / 3.36 / 3.81 | **−3.25**（−3.99 到 −2.63），少 43 % |
| 逐句矛盾率（%） | 15.2 / 20.1 / 10.2 / 12.8 | 12.6 / 18.2 / 8.51 / 9.15 | **−2.45 個百分點**（−3.72 到 −1.21） |
| 每場矛盾句數 | 12.0 / 33.2 / 5.3 / 7.2 | 2.3 / 3.7 / 1.5 / 1.4 | −12.2（−13.6 到 −10.8），少 81 % |
| 同樣長度下的覆蓋率 | 0.256 / 0.221 / 0.387 / 0.341 | 0.353 / 0.255 / 0.497 / 0.409 | **+0.077**（+0.037 到 +0.115） |
| 完整摘要的覆蓋率 | 0.739 / 0.746 / 0.752 / 0.668 | 0.358 / 0.262 / 0.488 / 0.414 | −0.346（−0.390 到 −0.303） |
| 每千字答對題數 | 2.93 / 1.10 / 6.26 / 6.93 | 4.63 / 2.04 / 8.52 / 11.4 | +2.35（+1.74 到 +3.01） |
| 每場字數 | 1,600 / 3,410 / 917 / 963 | 493 / 648 / 437 / 362 | 少 66 % |

- **判定：** 判定標準在產生任何輸出之前寫定，結果只讀取一次，讀取後沒有調整任何設定。三個條件都成立：
  - 每千字矛盾句數的區間整個低於 0，四個資料集各自也是。
  - 每個資料集的逐句矛盾率都沒有明顯變差：差異的區間上限是 −0.5 / +1.1 / +0.2 / −0.4 個百分點，門檻是 +3。
  - 同樣長度下的覆蓋率不低於 mobile-v2。
- **篇幅與覆蓋率：** v5 的摘要大約是 mobile-v2 的三分之一長，完整摘要能回答的題目因此只有一半左右。把 mobile-v2 的摘要截到與 v5 一樣長再比（「同樣長度下的覆蓋率」），v5 較高：同樣的篇幅，v5 帶到的內容比較多。
- **無依據的句子：** 只看引用時間附近的片段時，v5 被判為「無依據」的比例較高（4.1 / 6.0 / 3.9 / 5.1 % 對 3.2 / 4.3 / 3.2 / 2.8 %，高 1.4 個百分點）。放寬片段重新評審後：
  - v5 的這些句子有 56–83 % 在會議別處找得到依據，mobile-v2 是 35–56 %。
  - 仍然無依據的句子，v5 剩 0.5–0.7 %，mobile-v2 剩 0.7–1.5 %。
  - 另有一部分在放寬後被判為矛盾。把這些也算進去，兩者沒有顯著差異（−0.3 個百分點，−0.8 到 +0.1）。
- **限制：**
  - 覆蓋率只在有問卷的 104 場上計算。其餘 16 場沒有校準過的問卷，沒有用別的會議替補。矛盾率涵蓋全部 120 場。
  - AliMeeting 的 25 場與財經節目中的 10 場出現在 mobile-v2 的訓練資料裡，這對 mobile-v2 有利。只看兩個模型都沒見過的 85 場，結論相同：每千字矛盾句數 −3.05（−3.89 到 −2.35），逐句矛盾率 −1.98 個百分點（−3.39 到 −0.54）。
  - 測試的是 llama.cpp 的 Q4_K_M 檔，不是手機上要用的 `.litertlm`。`.litertlm` 的結果見「下一步：v6 計畫」。

### 開發集上的過程

每一輪在三個開發集上比較，下列數字依序是 ali20 / msdev / q12 的逐句矛盾率（去除填充句後）。

- **句子層級 DPO（`psent3n`，2026-11-16）：** 以評審逐句標記的「支持／矛盾」配對訓練 LoRA，可合併進權重，不增加手機上的運算。
  - 矛盾率：10.5 % / 15.0 % / 13.3 %；同樣算法下 Bolt 基礎模型是 13.8 % / 19.9 % / 20.0 %，mobile-v2 是 9.6 % / 16.2 % / 17.6 %。
  - 相對 Bolt 基礎模型：矛盾率低 5.1 個百分點（95 % 區間 3.9–6.4），覆蓋率少 3.3 個百分點。
  - 合併進權重並重新量化後效果不變：與執行時掛載 LoRA 相比，矛盾率差 +0.01 個百分點（−1.9 到 +1.9）。
- **拿掉「決定／待辦」清單：** 清單項目的矛盾率約為正文的兩倍，所以最終格式不輸出清單。
- **沒有帶來進步的嘗試：**
  - 改寫配對 DPO 與 best-of-8 SFT：與打亂標籤的對照組沒有差別。
  - 「一句一事實」提示：矛盾率反而上升。
  - 零樣本自我驗證：AUC 只有 0.61–0.69。訓練過的自我驗證器（AUC 0.70）要多花約 9 % 的手機運算，效果不如句子層級 DPO，未採用。
- **注意：** 同一模型、同樣的 seed，在不同批次間會有 1–2 個百分點的差異。每個實驗組都和同一批次產生的基礎模型比較。

**促進臺灣金融市場規模發展**
