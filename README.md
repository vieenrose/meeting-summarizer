# Meeting Summarizer

在手機上即時產生長會議的可靠摘要：會議進行中由裝置端 ASR 轉寫，小模型逐段讀取，會後輸出分段摘要。目標是 1.5–3 小時、以台灣華語為主並夾雜英文的會議。摘要裡每一句都標註它所依據的逐字稿時間。

**狀態（2026-11-16）：研究階段。** 目前發佈的版本是 mobile-v2（見 [docs/mobile-v2.md](docs/mobile-v2.md)），v5 尚未發佈。

## 架構（v5）

```mermaid
flowchart LR
    A[會議音訊] --> B[裝置端 ASR<br/>逐字稿]
    B --> C[在換講者處切段<br/>每段 ≤ 32k tokens]
    C --> D[Bolt 4GB 逐段讀取<br/>會議中預填 KV]
    D --> E[每段寫出 3–6 個主題小節<br/>以文法約束格式]
    E --> F[程式合併小節<br/>彙整決定與待辦]
    F --> G[依小節標題與首句<br/>產生會議標題]
```

- **模型：** Nemotron-3.5-Bolt-E4B（4 GB），Q4 量化，只在手機 CPU 上執行。
- **分段：** Bolt 實測的有效上下文是 32k。整場一次讀到 64k 時，後段的覆蓋率會從 0.64 掉到 0.51，所以每次最多只讀 32k。
- **長度：** 總長 800 字加上每小時 500 字，上限 2200 字。可讀性比長度優先。
- **格式：** 由文法強制主題標題與 `[時間]` 引用；「決定」與「待辦」由程式彙整。
- **會議標題：** 寫完所有段落後產生。模型只看各小節的標題與首句，不看逐字稿，在手機上只需幾秒。
- **即時性：** 在 Samsung Galaxy A53 上用 app 引擎（融合注意力）實測如下。處理時間不超過會議長度。

  | 上下文 | 預填 | 解碼 | 記憶體 |
  |---|---|---|---|
  | 4k | 36.3 tok/s | 3.67 tok/s | 2.6 GB |
  | 32k | 12.4 tok/s | 1.33 tok/s | 2.83 GB |

## 評估方式

每一輪都在三個保留集上評估，各跑 4 個 seed：財經節目（msdev）、立法院質詢（q12）、多人會議（ali20）。

- **矛盾率：** 由 Qwen3.8-27B 判斷每一句與引用時間附近的逐字稿是否相符，分為「支持」、「矛盾」、「無依據」三類。
- **覆蓋率：** 讀者只拿到摘要，回答一份涵蓋整場會議的選擇題問卷，以答對比例計分（d3-turbo，與大型評審的 kappa 為 0.91）。
- **原則：** 不修正 ASR 輸出，也不排除長會議。

## 最新結果

**目標：單次讀取的 Bolt 在矛盾率上勝過 mobile-v2。** mobile-v2 是在 Gemma-4 E4B 上執行的閱讀代理。

| 資料集 | mobile-v2 | Bolt 基礎模型 | Bolt＋自我驗證刪句（初步） |
|---|---|---|---|
| ali20 | 10 % | 12–13 % | 10.4 % |
| msdev | 16 % | 16.5–17.5 % | 13.6 % |
| q12 | 18 % | 18–19 % | 14.9 % |

- **以每場會議計算，Bolt 已經更少錯誤。** mobile-v2 寫出的句子大約是 Bolt 的兩倍：在 msdev 上每場有 12.3 句矛盾，Bolt 是 6.9 句；在 q12 上是 21.5 句對 11.6 句。
- **自我驗證（S2）：** 在 Bolt 上訓練一個 LoRA 驗證器。它沿用生成時的 KV 快取，一次判斷整段裡的每一句，刪除 P(否) ≥ 0.5 的句子。
  - 區分能力 AUC 為 0.70，打亂標籤的對照組只有 0.56。
  - 刪掉 5–9 % 的句子。
  - 上表這一欄是依現有評審標籤推算的；重新評審與覆蓋率測量正在進行。
- **句子層級 DPO（`psent3n`，2026-11-16）：** 以評審逐句標記的「支持／矛盾」配對訓練 LoRA，可合併進權重，不增加手機上的運算。
  - 矛盾率（ali20 / msdev / q12，去除填充句後）：10.5 % / 15.0 % / 13.3 %；同樣算法下基礎模型是 13.8 % / 19.9 % / 20.0 %，mobile-v2 是 9.6 % / 16.2 % / 17.6 %。
  - 相對 Bolt 基礎模型：矛盾率低 5.1 個百分點（95 % 區間 3.9–6.4），覆蓋率少 3.3 個百分點。
  - 相對 mobile-v2：每千字矛盾句數少 1.8 句（1.0–2.7）；逐句矛盾率低 1.5 個百分點（−3.6 到 +0.5，三個資料集等權），還不顯著。
  - 尚未驗證：合併後重新量化的版本，以及需要 3 段以上的長會議。新舊兩代在同一場會議上的摘要見下方「新舊兩代並排」。
- **沒有帶來進步的嘗試：**
  - 改寫配對 DPO 與 best-of-8 SFT：與打亂標籤的對照組沒有差別。
  - 「一句一事實」提示：矛盾率反而上升。
  - 零樣本自我驗證：AUC 只有 0.61–0.69。
- **注意：** 同一模型、同樣的 seed，在不同批次間會有 1–2 個百分點的差異。每個實驗組都和同一批次產生的基礎模型比較。

同一份逐字稿，兩代各自寫出的摘要，都是使用者在手機上會看到的形式。文字未經修改，只把小節標題改為粗體。

- **上一代（mobile-v2）：** Gemma-4 E4B 閱讀代理，也就是目前發佈的版本。這裡顯示的是段落式摘要：代理讀完會議後，用整合文件 §6.6 的提示把筆記寫成段落。因為這場會議超過 3 小時，使用**長會議版**的提示：輸出上限隨會議長度放寬（這一場是 1,357 tokens，一般版固定 600），並要求依時間順序涵蓋前、中、後段。即使如此，4k context 在寫到 2:48 時用完，最後一句沒有寫完，原樣保留。一般版（600 tokens）在這一場只寫到 1:53。

**這一場看得到的差別：**

- **只有一場會議，句數很少：** 矛盾 4 句對 7 句，方向和整組開發集一致，但單場不足以下結論。兩代在整組開發集上的比較見上方「最新結果」。
- **可讀性：** v5 分成 6 個主題小節，最後彙整決定與待辦，可以直接找到「誰要在什麼時候交什麼」。mobile-v2 是一整段連續文字，依時間逐條敘述，開頭是議事程序（確認議事錄、執行方式）。
- **涵蓋範圍：** mobile-v2 的長會議版寫到 2:48 才中斷（一般版停在 1:53），但 31 分到 1:24 之間的專題報告完全沒有提到，最後 40 分鐘也沒有內容；問卷 9 題一題都答不出來。v5 的主題涵蓋 34 分到 2:24，再加上散會時的決定。
- **v5 的弱點仍在——每段的後半覆蓋不足：** 2:24 之後到散會之間約一小時的質詢（外資賣超、新臺幣貶值）沒有寫到。
- **v5 的矛盾多半是數字放錯脈絡：** [1:19:24] 把「增加將近 50 兆」寫成「總資產將近 50 兆」（逐字稿是 73 兆）；[2:23:59] 把個人與公司的結匯額度混在一起。mobile-v2 的 7 句多半是主體或語氣寫錯：[2:30:37] 把財政部同意寫成央行同意，[1:42:36] 把承諾送報告的人寫成國發會處長，[2:39:46] 把委員的期望寫成已達成的協議。
- **精簡的代價：** 和較長的格式相比（2,215 字、17 個主題、問卷答對 5 / 9），精簡格式少了一半以上的篇幅，問卷答對降到 3 / 9。
- **ASR 錯誤：** 兩邊都原樣帶入（例如「鄭棋局」「經管會」）。我們不修正 ASR 輸出。
