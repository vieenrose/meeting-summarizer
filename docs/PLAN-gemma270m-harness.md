# Joint plan: Gemma-3-270M + harness, trained on one shared contract

**Status:** plan, 2026-08-01. Supersedes the independent fine-tune / harness tracks, which
collided (the model was trained for one-shot NOTES and the harness asked for a near-miss
format; the model's prior won and emitted header-less bullets).

## 1. Why Gemma-3-270M is the right target for this role

| property | value | why it matters |
|---|---|---|
| **zh tokenizer** | **1.53 chars/token** | 262k multilingual vocab. Beats LFM2.5 (0.94), Granite-4h (0.69), Qwen3-0.6B (1.40); close to Qwen3.5-0.8B (1.67) |
| **`.litertlm` path** | **`convert_gemma3_to_tflite.py` exists** in ai-edge-torch | removes the blocker that stopped Qwen3.5 — no llama.cpp reintroduction needed |
| attention | 18 layers, **MQA (1 KV head)**, sliding window 512, 5:1 pattern | KV @8k ≈ **33 MB f16 / ~8 MB q4** |
| size | 270M = **168M embeddings + ~100M transformer** | weights ≈ 220 MB (int8 embeddings + q4 body) |
| positioning | Google ships it explicitly for **task-specific fine-tuning**, "not designed for complex conversational use cases" | matches exactly how we use it |
| context | 32k native | far more than the 8k the harness needs |

Projected peak RSS: **≈ 400–500 MB**, roughly half the current Qwen3.5-0.8B build (872 MB
measured) — and it can ship through LiteRT-LM instead of GGUF.

**The honest risk:** the transformer is only ~100M parameters (63% of the model is the
embedding table). Zero-shot it will be poor at Chinese summarization. The bet is that the
harness reduces the job to something a 100M transformer can learn, and that is exactly what
this plan tests.

## 2. The contract — one definition, used by both sides

The harness makes exactly **three kinds of call**. These are the *only* things the model is
ever asked to do, and the training data consists of exactly these, generated by running the
real harness. No one-shot 32k summarization anywhere in the data.

| op | input | output | why it's learnable at 100M |
|---|---|---|---|
| **A. `chunk_notes`** | one ≤4k-token transcript chunk | typed notes: 5 sections, `- bullet [mm:ss]` | everything needed is visible in the prompt; no long-range recall |
| **B. `merge_section`** | one section's bullets + the transcript lines their anchors point at | ≤N merged bullets, anchors kept | a bounded rewrite with evidence in view — not a judgement |
| **C. `title`** | the finished notes (~300 tokens) | one line, ≤8 words | trivial |

Everything else — chunking, de-duplication, time-ordering, contradiction resolution,
section assembly, fallbacks — is deterministic Kotlin. **The model never emits a memory
operation**, which is what makes sub-1B viable (measured: ~30% malformed memory writes at
3B; 3.6% BFCL multi-turn at 0.6B).

Single source of truth: `agentic/contract.py` defines the three prompt templates and the
parser. `distill/gen_harness_data.py` imports it to build data; `agentic/harness.py` and
the Kotlin port import/mirror it to run. A change to a prompt is a change to both, by
construction. **This is the fix for the collision.**

## 3. Data generation — trajectories, not synthetic prompts

Run the **actual harness** over the training meetings with the 9B teacher in the model slot,
and capture every `(prompt, completion)` pair at each call site. This guarantees the training
distribution equals the deployment distribution — including the awkward cases (a chunk that
contains nothing decision-like, a section with one item, a chunk that starts mid-sentence).

1. **Teacher pass**: harness + Qwen3.5-9B over ~3,000 meetings (en + zh-TW) →
   ~30k op-A samples, ~15k op-B, ~3k op-C.
2. **Faithfulness filter**, as before: judge each completion against *its own visible input*
   (which for op-A is just the chunk — a much sharper check than judging against a whole
   meeting). Drop faith<4 or any inversion. Expect ~15% dropped.
3. **Op-B negatives are free and valuable**: any merge where the teacher failed to apply
   "later supersedes earlier" becomes a rejected sample for later preference training.
4. **Balance**: cap op-A per meeting so long meetings don't dominate; keep en:zh ≈ 1:1.

## 4. Training

- Base `google/gemma-3-270m-it`; full fine-tune (LoRA is for >1B — full FT is cheap here).
- **max_len 8192** — the harness never exceeds it, so no wasted compute and no 32k packing.
- 3–4 epochs (small model, narrow task), lr ~2e-5, cosine.
- **QAT from the start**: int4-block32 body, **int8 embeddings** (168M of the params — the
  one part that must not go to 3–4 bits), q4 KV fake-quant.
- Loss on completions only.

## 5. Evaluation — unchanged instrument, so numbers stay comparable

Primary, on the same 16 held-out long meetings:
- **inversion rate** and **faith≤2**, versus the current build's 0% / 0% (n=16) and the
  single-pass baseline's 25%.
- **per-op accuracy**: op-A format compliance and anchor validity; op-B supersede-rule
  correctness (a targeted probe set built from meetings where a decision is reversed).
- **cost**: peak RSS, prefill tokens, wall-clock at 4 threads.

**Kill criteria — state them now, before the results:**
- op-A format compliance < 90% after training → the transformer is too small; fall back to
  Qwen3-0.6B (1.40 c/t, also has a converter path).
- inversion rate > 5% on long meetings → worse than the shipped build; not a candidate.
- zh coverage materially below en → the 262k vocab did not carry Chinese competence at 100M.

## 6. Order of work

1. `agentic/contract.py` — extract the three ops as the single shared definition.
2. Rewrite `agentic/harness.py` to import it (drops the bespoke prompts entirely).
3. `distill/gen_harness_data.py` — teacher-driven trajectory capture + faith filter.
4. Train Gemma-3-270M (QAT, 8k).
5. Evaluate against kill criteria; in parallel convert to `.litertlm` to confirm the
   deployment path end-to-end.
6. If it passes: publish + integration note. If it fails a kill criterion: rerun the same
   pipeline on Qwen3-0.6B — the data and harness are model-independent by design.
